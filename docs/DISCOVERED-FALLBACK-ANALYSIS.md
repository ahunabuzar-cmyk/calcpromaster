Dono groups structurally wahi hain — 133/133 gire hue URLs aaj bhi sitemap mein hain, aur unke 14 median internal inlinks hain. Yani page-side pe kuch toota nahi.

## 4. To phir wajah kya hai

Jo cheezein page-side badalti hain wo test ho gayi aur **koi nahi badli**: sitemap presence wahi, inlink count wahi, aur koi URL index se "gira" bhi nahi (became-indexed 0 aur index se bahar hone ka koi case nahi). Bacha ek hi factor: **Google ke crawl queue mein URL ki jagah**.

GSC ka URL-Inspection `coverageState` "Discovered – currently not indexed" tab deta hai jab URL us waqt discovery record ke saath queue mein ho; queue se nikal jane par wahi URL "URL is unknown to Google" dikhane lagta hai — jabke page aaj bhi sitemap mein aur linked hai. Isi liye:

- ek hi do-din window mein **133 andar / 105 bahar** ka churn hua;
- 20-URL hub sample par (jo pehle se zyadatar indexed tha) slippage **0** thi — churn sirf crawl-queue backlog mein dikhta hai;
- koi bhi URL indeks se hat kar `unknown` nahi hua; sirf queue position badli.

**Isliye:** 133 ko "kuch toot gaya" ki tarah treat karna ghalat hai, aur burndown ka `slippedBack` column usi soorat mein **crawl-budget churn** ka indicator hai, na ke page-level regression ka.

## 5. Is se kaam kya badalta hai

1. **"Discovered" ko progress ka paimana mat banao.** Wo queue membership hai, page ka status nahi. Jo metric churn se paak hai wo hai **indexed pages** aur **impressions** — wahi headline rakho.
2. **Links ka kaam alag hai.** Links se page *discover* hota hai aur crawl priority milti hai; wo "Discovered" label ko freeze nahi karte. Is liye link-building ko chhodo mat — bas us se queue label ko score mat karo.
3. **Request-indexing ko measure karo, maano nahi.** Jo URLs request hue the unka index rate alag se track karo (`docs/INDEX-PANEL.md`), warna ye sawal har hafte wapas aayega.
4. **Har snapshot ke saath churn likho.** `build-index-burndown.cjs` ka `slippedBack` sath mein `gainedBack` bhi rakhe, taake do-tarfa harkat ek hi nazar mein dikhe.
